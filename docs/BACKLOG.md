## Added at M2

| # | Missing | Why deferred | Lands at |
|---|---|---|---|
| 12 | **HS256, one shared secret.** auth-service signs and the other two verify with the same key, so any of them could in principle mint a token | acceptable while all four services deploy together from one repository. RS256 — private key in auth-service, public half published as a JWK set — is the production answer, and the verifying code does not change, only the decoder's source of key material. Weighed against it: an in-memory keypair dies on restart and invalidates every issued token, which is a live hazard during a defence | when the services deploy separately |
| 13 | **Registration is a dual write with no retry.** work-service gets the profile, then auth-service saves the credential. If the second write fails, a profile exists that nobody can log in as | the real fixes are an outbox table or an idempotent retry that reuses an existing profile, and both are a milestone of their own. The failure is logged with the orphaned id rather than swallowed, so it can be found | when a second cross-service write appears |
| 14 | **No refresh token.** A token lasts one hour and then you sign in again | a refresh token needs storage, rotation and a revocation list, which is the point at which sessions become a subsystem. One hour is longer than any demo and short enough that a leaked token expires by itself | if a real user complains |
| 15 | **One role rule only:** `DELETE /users/**` requires ADMIN | the domain model does not yet say who may close a sprint or delete a project. Inventing rules the class diagram does not state would be guessing, and a wrong rule is worse than a missing one. The mechanism is built and proven by this one rule | when the domain says who may do what |
| 16 | **No rate limit and no lockout on login** | brute force is a real attack on a real deployment. It needs a shared counter, which means Redis or a database table, and a lockout policy that can itself be used to lock someone out on purpose | before anything is exposed outside localhost |
| 17 | **auth-service does not store the email**, it forwards it to work-service and forgets it | keeping a copy would make two rows to change when someone updates their address, with no owner for the disagreement. The cost is that password reset by email would have to ask work-service first | when password reset is built |
| 18 | **The token is kept in `localStorage`** | any script on the origin can read it. The alternative, an HttpOnly cookie, cannot be read by JavaScript but is attached automatically, which is what makes CSRF possible and would mean bringing back the defences the stateless API deliberately does without. Short token lifetimes are the mitigation | if the app is deployed publicly |
| 19 | **One Eureka instance, one gateway instance** | both are single points of failure and both are stated as decisions in `ARCHITECTURE-NOTES.md`, not discovered as gaps. Clustering Eureka is a configuration change, not a redesign | never, for this project |
| 20 | **The gateway does not proxy Swagger UI** | routes are declared by resource path (`/projects/**`, `/issues/**`), and adding `/v3/api-docs` would put the contract behind the edge for no gain. The docs are read on 8081 directly | if the services stop being reachable directly |

## Added at M3

| # | Missing | Why deferred | Lands at |
|---|---|---|---|
| 21 | **No transactional outbox.** `issue.created` is published after commit, so a crash between the commit and the publish loses the message and the issue is never classified | the outbox is a table, a poller and a dedupe key — a milestone of its own. It is survivable here because an unclassified issue is *degraded, not corrupt*: the ticket exists and can be worked, only its suggestion is missing. The failed publish is logged with the issue key so the message can be replayed by hand | when a lost classification actually costs something |
| 22 | **`replay` moves messages one at a time, outside a transaction.** If the publish fails after the receive, that message is gone | a transacted channel would fix it. At one queue and a manual admin action the honest note is worth more than the machinery, and the failure is logged with the full message body so it can be reconstructed | with the outbox |
| 23 | **Nothing drains the dead-letter queue automatically.** Somebody has to call `POST /admin/classification/replay` | on purpose. A queue that empties itself while nobody is watching is a queue that loses things quietly, and a timed auto-replay against a provider that is still down just re-parks everything. A scheduled replay with a backoff is the real version | when there is someone on call |
| 24 | **The stub classifier is the default.** With no `GROQ_API_KEY`, suggestions are keyword rules | so the project runs on a fresh clone. Mitigated three ways rather than hidden: a warning block on startup, `modelVersion=stub-v1` on every row, and that version printed on the chip in the UI. **The real path is now proven**: 153/153 against `openai/gpt-oss-120b` | — |
| 25 | **`Issue` has no `component` field**, though `PROJECT.md`'s M4 dashboard says "type/component distribution" | the class diagram does not give `Issue` one, and inventing a column the source of truth does not describe is how a model and a diagram drift apart. **Decided at M4: not adding it.** The dashboard shows type, priority and status from the issue, and team and effort from what the AI inferred — `suggested_team` is the nearest real axis and it is on the screen. Adding a column to serve a chart is the wrong order | only if the domain gains components for a real reason |
| ~~26~~ | ~~**Groq has no embeddings API**~~ | **Done at M4**, and the fix is better than the thing it replaced: `all-MiniLM-L6-v2` runs in-process as ONNX. No key, no cost, no rate limit, no network call. The diagram has been corrected to say Groq is LLM-only | — |
| 27 | **The suggestion chip polls**, it is not pushed | a push channel is the notification service, which `PROJECT.md` puts in Stretch. A suggestion that lands two seconds late does not justify a WebSocket, and the poll stops after 30 seconds rather than spinning forever | with the notification service |
| 28 | **No JUnit tests for the classification path** | `scripts/smoke-test.sh` covers the whole pipeline against a running system — 127 cases — but it needs four services and a broker, and it does not run in `mvn verify` | the same task as item 9 |

## Added at M4

| # | Missing | Why deferred | Lands at |
|---|---|---|---|
| 29 | **The first start of classification-service needs internet** to download the ~80MB ONNX model. Every start after that is offline | bundling the model in the jar would put 80MB of binary in git, and pinning it to a local path would break a fresh clone. Cached under `java.io.tmpdir`, so a machine that has run once keeps working. **Run it once before a demo** | if the cache directory turns out to be cleared too often |
| 30 | **Renaming an issue does not re-embed it.** Only creation does | the vector would drift from the title, and the duplicate panel would match on text nobody can see any more. `POST /admin/issues/reindex` fixes it in one call. Doing it automatically means publishing on update too, which is a fourth event for a case that is rare | when titles are edited often enough to notice |
| 31 | **`SimilarIssue` reads its title out of the vector's metadata**, so a renamed ticket shows its old title until reindexed | the alternative is calling work-service for every match, which turns a search that has to answer while somebody is typing into two hops. Same root cause as item 30 | with 30 |
| 32 | **The similarity threshold is one number for the whole system**, measured against one ticket | a real tuning would use a labelled set of known duplicates and pick the threshold from a precision/recall curve. The measurement behind 0.45 is written into `application.properties` and `ARCHITECTURE-NOTES.md` §9, so the reasoning can be checked even though the sample was small | when there are real duplicates to measure against |
| 33 | **No reranking.** The top five by cosine distance are the answer | a cross-encoder would judge each candidate properly instead of comparing two vectors, and would be more accurate. It is also a second model and a second call, for a panel that already answers well enough to be useful | if the matches turn out to be noisy in practice |
| 34 | **`replay` and `reindex` have no progress and no cancel.** Both return a count and get on with it | the work happens on the other side of the queue, so a truthful progress bar would mean tracking each message. The queue depth in the RabbitMQ management UI is the honest substitute | when a reindex takes long enough to worry about |
| 35 | **Still no client-side routing**, now with four screens | the argument gets stronger with each screen: you cannot refresh into the dashboard or link somebody to it. The answer to "why is there no router" should stay a decision rather than becoming an oversight, and this is the milestone where it stops being obviously right | the next screen |
| 36 | **The dashboard is system-wide**, not per project | every metric is a `group by` with no `where`. Scoping it to a project is a query parameter and a filter, but "type distribution" means something different per project than across a team, and picking which one the screen is for is a product decision | when there is more than one real project |

## Added after running against the real Groq

| # | Missing | Why deferred | Lands at |
|---|---|---|---|
| 40 | **Groq's free tier allows 8000 tokens per minute**, and a burst of tickets exceeds it | not a code problem, and the system already handles it correctly: the 429 is classified as transient, retried with backoff, and anything that outlives its retries is parked for replay. `reasoning-effort=low` cut usage from 306 tokens a ticket to 80, which is a 4x larger burst before the limit bites. The real fix is a paid tier | if the demo needs more than a few tickets a minute |
| 41 | **No client-side rate limiting or queue throttling** toward Groq | the broker already limits concurrency to two consumers, which is why a burst degrades into retries rather than a flood. A token-bucket that paced against the published TPM would be better, and it is a real piece of work for a problem the retry path already survives | if the free tier stops being enough |
| 42 | **The API key is passed as an environment variable**, so it is visible in the process environment | correct for local development and what twelve-factor asks for. A real deployment reads it from a secrets manager, and the code does not change — it is already `${GROQ_API_KEY}` and never a literal | when it is deployed anywhere real |
